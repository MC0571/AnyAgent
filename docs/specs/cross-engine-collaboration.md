# 跨 Engine 协作契约

目的与范围：规定 Task／Workflow 协调参与者、显式消息与产物的外部行为；不规定消息总线、锁实现或 Harness 私有上下文结构。

设计状态：Proposed（2026-09-22），遵循 [ADR 0003](../decisions/0003-cross-engine-collaboration-is-task-scoped.md)。本规格把 Task／参与者与 Session 的业务使用关联同 Session 的 Engine 身份和原生状态分开；首版默认新独立 Task 新建参与者和 Session，暂不支持跨 Task 使用既有 Session。实现与验证状态：M0 已导入上游过渡源码，但尚未实现或验证本规格的跨 Engine 协作；CO 场景为待实现验收要求。身份、基数与状态权威定义见[领域模型](../domain/README.md)和[生命周期](../domain/lifecycle-and-ownership.md)，输入与原生事件证据见[Engine 契约](engine-adapter.md)，资源边界见[共享能力](shared-capabilities.md)。

本规格在协作能力实施时约束其行为；“首版待实现验收”不表示近期 Engine 接入 Milestone 必须实现委派、消息、Workflow 调度、预算或多参与者整合。具体交付范围以 GitHub Milestone／Issue 为准，单参与者路径仍须遵守适用的业务接纳、审批、取消与来源归属约束。

## 参与者与调度

### COL-01 责任明确后才能委派

委派的接纳与实际派发须遵循 [LIFE-ADMISSION](../domain/lifecycle-and-ownership.md#life-admission-业务接纳资格proposed) 的 Task／参与者资格及冻结约束。产品调度方在接纳委派前必须记录 Task、发起者、目标 Agent Instance、职责、Engine、目标 Session（如已建立；否则标记为“未建立”）、允许访问的资源、预算及结果整合责任人。参与者遵循领域基数提案；同一 Task 可以有同 Engine 或不同 Engine 的参与者，各 Session 始终保留原 Engine 归属。Task／参与者与 Session 的关系表示本次业务使用，不能依据 Session 的最新使用者动态改写历史归属。新的独立 Task 首版默认创建新的参与者和 Session；原生子 Agent 只有在公开能力允许映射时才显示为可观察成员，不能默认为可独立取消或授权的产品参与者。

目标参与者可以尚无已建立的 Session；委派接纳不要求预先存在原生 Session。若目标 Session 标记为“未建立”，实际派发前必须完成 Session 创建及 Engine、环境、授权和合法使用关联校验；创建失败时保留委派记录并拒绝派发，不能用未建立的标识伪造关联。

Workflow 记录依赖、投递策略、失败策略和验收门槛；人工任务也可由用户逐次确认这些条件。确定性调度负责依赖与预算检查，不需要额外 LLM 主 Agent。若配置智能协调参与者，它与其他参与者同级、受相同范围与预算约束，其建议须经过产品契约校验才能形成委派。

### COL-02 依赖和预算

调度方只在前置结果按指定门槛被接纳、资源条件满足且授权有效时启动后继工作。“上游 Execution 完成”不能替代“上游产物被接受”。默认失败策略为阻塞依赖后继，独立分支可以继续；重试、跳过或终止整任务须是 Workflow 明确策略或用户决定。接纳前拒绝依赖环路或无法满足的目标引用。

每次委派必须有可执行的并发上限、委派次数／深度上限和截止条件；后续实现为其选择具体默认值。费用、token 等只有在可获取和可强制的条件下才作为硬预算，否则标为估计或观察限制，不承诺严格封顶。预算耗尽时停止接纳新工作，并按既定策略请求停止在途执行；越界原生子 Agent 无法观测时须显示控制范围缺口，不能宣称整个 Harness 受产品计数覆盖。

## 消息、交接与协作形式

### COL-03 消息证据逐级可见

产品消息记录发送者、接收者、Task、参与者、目标 Session、材料引用、授权范围和关联输入；尚未形成 Execution 时也保留这些原始关联和投递证据。下列投递证据只由负责组件确认，不依 UI 动画推断：

| 证据 | 确认者及含义 |
| --- | --- |
| queued | 产品消息队列已接纳；持久化后才能承诺重启不丢失 |
| delivered | Adapter 有证据证明 Engine 接口收到；不等于进入模型上下文 |
| included | 原生证据或已核实调用语义表明该消息成为某 Execution 输入，关联该 Execution |
| replied | 存在明确关联该消息的回复；无关联的后续文本不能冒充回复 |

若原生仅提供部分证据，其他阶段标为未知，不补造过渡，也不把 delivered 表述为“已理解”。队列去重以产品消息标识为范围；重连及结果未知遵循 [ENG-06](engine-adapter.md#eng-06-关联顺序和重连)。无运行中介入能力时须使用调用者明确选择的下一轮投递或拒绝策略；默认不得悄悄改投其他 Session。无法等待下一轮的消息应超时并保留原因，而非永远显示已送达。

消息、审批答复、工具结果、用量、Artifact 和错误须按原始输入或 Execution 关联到对应 Task／参与者／Session；UI 切换任务、Host 重启或后续使用关系变化不能改变归档目标。无法可靠关联的事件标为关联未知并进入对账，不能按当前 Task 或 Session 最新使用者猜测。

### COL-04 协作形式独立组合

串行通过依赖约束交付，并行通过隔离工作及整合门槛汇合，交互式通过显式消息与已声明介入能力交流，交接通过新建目标会话延续工作。它们不是实现阶段等级。当前 Task 可以协调多个独立 Session 和多个 Harness，与是否支持 Session 跨 Task 复用无关；首版同一 Session 只允许一个明确参与者驱动业务执行，并按单 Session 串行输入处理。产品在发起前展示所选组合的能力缺口；任一形式都不要求不同 Harness 共享原生内存、压缩状态或私有上下文。

### COL-05 Handoff

发起方先形成可审阅材料清单：目标、摘要、文件及版本、Diff 基线、TODO、来源和无法迁移项。调度方在目标 Engine、资源权限、披露范围获准后创建新参与者及新 Session，再投递材料，记录源 Task／参与者／Session 与目标 Task／参与者／Session 的业务关联。Handoff 即使目标使用同一 Engine 也创建新 Session，不偷偷复用源会话；首版不以 Handoff 绕过跨 Task Session 限制。默认不传凭据、原生私有上下文、隐藏推理、内部工具句柄或未授权浏览器状态；历史文本也须按接收范围筛选。目标失败不删除源记录，目标收到材料不等于完成原任务；源执行是否继续或停止必须显式选择，Handoff 本身不隐式终止源执行。

## 共享资源与结果

### COL-06 一个整合责任入口

调度方为每项共享可变资源记录本次业务的 Task／参与者／Execution 归属、允许的读写操作、基线及整合责任人。首选为不同参与者使用独立工作副本并提交 Artifact／Diff，由指定整合者串行应用；必须共用资源时，写入或浏览器控制只授予一个当前持有者，其他请求排队或明确拒绝。资源标识与授权见 [CAP-02](shared-capabilities.md#cap-02-资源身份与范围)。Session 曾获准使用资源不使新 Task 自动继承该授权；未知执行造成的冲突或占用限制在独立证据解除前继续有效。同一批文件的范围重叠、标签控制权重叠均视作冲突，不能只比较参与者名字。

提交时发布带来源、基线和结果版本的不可变产物引用；整合者检查基线是否仍适用、授权及验收条件。基线变化时必须报告冲突并请求重新整合，禁止静默覆盖。接受结果属于产品验收动作，可由授权用户或预配置确定性检查完成，不能由产物发布者自行伪造。共享路径不能约束 Engine 直接文件写入时，调度方应禁止该并行组合或要求真实隔离；不能声称应用锁已阻止所有外部修改。用户或外部进程的修改同样触发基线复核。

## 失败、取消与用户介入

### COL-07 控制生效范围可核查

用户可查看参与者、Session、执行证据、消息、产物、权限请求和责任链，并请求暂停后续派发、修改尚未接纳的工作或取消 Task。已接纳或执行中的工作改动应以新输入／显式介入表示，保留原记录。取消传播由调度方冻结新委派和待投递消息，对在途 Execution 分别提出停止请求，按[生命周期规则](../domain/lifecycle-and-ownership.md)记录请求与确认。

调度方必须按 [LIFE-03](../domain/lifecycle-and-ownership.md#life-03-取消停止与副作用) 的完整停止判据核对聚合结果，才能报告整个 Task 已停止；远程失联或不支持中止的参与者必须列为仍运行或结果未知。取消传播按 Task／参与者／Execution 范围记录；Task 取消不等于任意销毁可能被多个业务使用的 Engine 进程，进程级操作须先明确所有权和影响范围。用户也可按 LIFE-03 明确放弃产品协调并归档，保留未知风险、未解除资源限制及必要停止／对账入口；这不属于“整个 Task 已停止”的确认，也不证明受影响 Session 已空闲或可交给新 Task。完成先于取消确认的竞态应保留已完成结果及取消未生效的证据。已发生文件／外部系统变化单列，停止不代表撤销；补偿操作需重新核对授权、现状和副作用，不能作为通用回滚保证。

### COL-08 部分失败与重试

失败参与者保留错误、已有产物和副作用记录，未受依赖影响的分支按 COL-02 继续。调度方展示等待、重试、调整职责或终止的选项及作用范围。原 Execution 不改写为新一次执行；重试建立新 Execution，记录本次经重新校验的实际 Task／参与者／Session 使用关联并引用前次，不改写旧 Execution 归属，也不强制继续使用原 Session，可按能力和资格重建或有序替换会话，先确认重试条件及副作用。接纳回执丢失的未决投递及未知结果先查询或核实，不能当成确认失败自动重试；显式放弃协调也不授予重试资格，旧执行及资源冲突仍须核对。整个 Task 的验收依据所有必需分工及整合结果，某个 Engine 正常结束不能自动判定成功；豁免失败分工必须留存授权者与变更后的验收依据。

## 验收场景

用两个可控假 Engine、一组版本化资源和可注入故障的队列验证以下行为；真实 Harness 能力须另行验证。

### 首版待实现验收（Proposed）

| 标识 | 场景 | 可观察断言 |
| --- | --- | --- |
| CO-01 | 同 Task 下两个不同 Engine 的独立 Session 并行，随后整合 | 各 Session 原 Engine 不变；每次执行归属对应参与者和 Task；依赖只在规定结果获接受后解除 |
| CO-02 | Engine 不支持实时介入，发送消息 | 展示并执行明确的排队／拒绝策略；投递与纳入输入证据分开 |
| CO-03 | 两参与者修改重叠文件或控制同标签，外部用户同时更改基线 | 未授权写请求排队／拒绝；整合发现冲突，无静默覆盖 |
| CO-04 | 一分支失败，另一独立分支运行 | 依赖后继阻塞，独立分支遵照策略；重试有新 Execution 和副作用核对 |
| CO-05 | 取消时一执行停止、一执行失联、一执行先行完成 | UI 分别显示证据，不将整个 Task 标为已停止，不承诺回滚 |
| CO-06 | 跨 Engine Handoff，含未授权资料 | 新参与者和新 Session；未授权材料不传递；源 Task／参与者／Session 状态和迁移缺口保留，不能偷偷复用源会话 |
| CO-07 | 递归委派耗尽预算或引入环依赖 | 新委派被拒并显示原因，现有执行按既定策略处理 |
| CO-08 | 消息 queued 后 Host 重启，送达后断线 | 已承诺持久化的消息可恢复；无证据不补 included／replied，不盲目重发 |
| CO-09 | 远端永久失联，用户先不处置，再明确放弃协调并归档；另一参与者申请写旧资源，随后旧执行迟到完成 | 不自动收尾；显式管理收尾保留未知记录并冻结派发，归档不释放冲突写权限或证明 Session 空闲；仅实际终止或隔离证据可解除对应限制，迟到证据更新原事实但不重开任务 |

### 未来跨 Task 串行复用准入验证（Proposed，非首版能力）

未来准入验证统一复用 [Engine 契约的 EA-14](engine-adapter.md#未来跨-task-串行复用准入验证proposed非首版能力)；该场景不在协作表中重复定义，也不表示首版支持或要求当前 Adapter 实现跨 Task API。完整条件仍集中在[领域模型 DOM-05](../domain/README.md#dom-05-未来跨-task-串行复用条件proposed)。

## 未决项

待批准：默认采用独立工作副本加串行整合，以及同 Session 串行输入的提案。待具体实现验证：哪些执行宿主能强制隔离写入、哪些原生协议提供 included／replied 关联。委派默认额度、队列有效期及任务验收规则应由产品配置明确，不能在 Adapter 内隐式固定。Workflow 编辑与在途实例的版本策略首选“已接纳工作保留原版本，新工作显式采用新版本”，避免编辑追溯改变授权。
