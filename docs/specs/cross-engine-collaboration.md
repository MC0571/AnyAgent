# 跨 Engine 协作契约

目的与范围：规定 Task／Workflow 协调参与者、显式消息与产物的外部行为；不规定消息总线、锁实现或 Harness 私有上下文结构。

设计状态：Proposed（2026-09-22），遵循 [ADR 0003](../decisions/0003-cross-engine-collaboration-is-task-scoped.md)。实现与验证状态：尚无业务代码或协作测试；CO 场景为待实现验收要求。身份、基数与状态权威定义见[领域模型](../domain/README.md)和[生命周期](../domain/lifecycle-and-ownership.md)，输入与原生事件证据见[Engine 契约](engine-adapter.md)，资源边界见[共享能力](shared-capabilities.md)。

## 参与者与调度

<a id="COL-01"></a>
**COL-01 责任明确后才能委派。** 委派的接纳与实际派发须遵循 [LIFE-ADMISSION](../domain/lifecycle-and-ownership.md#LIFE-ADMISSION) 的 Task／参与者资格及冻结约束。产品调度方在接纳委派前必须记录 Task、发起者、目标 Agent Instance、职责、Engine、允许访问的资源、预算及结果整合责任人。参与者遵循领域基数提案；同一 Task 可以有同 Engine 或不同 Engine 的参与者，各 Session 始终保留原 Engine 归属。原生子 Agent 只有在公开能力允许映射时才显示为可观察成员，不能默认为可独立取消或授权的产品参与者。

Workflow 记录依赖、投递策略、失败策略和验收门槛；人工任务也可由用户逐次确认这些条件。确定性调度负责依赖与预算检查，不需要额外 LLM 主 Agent。若配置智能协调参与者，它与其他参与者同级、受相同范围与预算约束，其建议须经过产品契约校验才能形成委派。

<a id="COL-02"></a>
**COL-02 依赖和预算。** 调度方只在前置结果按指定门槛被接纳、资源条件满足且授权有效时启动后继工作。“上游 Execution 完成”不能替代“上游产物被接受”。默认失败策略为阻塞依赖后继，独立分支可以继续；重试、跳过或终止整任务须是 Workflow 明确策略或用户决定。接纳前拒绝依赖环路或无法满足的目标引用。

每次委派必须有可执行的并发上限、委派次数／深度上限和截止条件；后续实现为其选择具体默认值。费用、token 等只有在可获取和可强制的条件下才作为硬预算，否则标为估计或观察限制，不承诺严格封顶。预算耗尽时停止接纳新工作，并按既定策略请求停止在途执行；越界原生子 Agent 无法观测时须显示控制范围缺口，不能宣称整个 Harness 受产品计数覆盖。

## 消息、交接与协作形式

<a id="COL-03"></a>
**COL-03 消息证据逐级可见。** 产品消息记录发送者、接收者、Task、材料引用、授权范围和关联输入。下列投递证据只由负责组件确认，不依 UI 动画推断：

| 证据 | 确认者及含义 |
| --- | --- |
| queued | 产品消息队列已接纳；持久化后才能承诺重启不丢失 |
| delivered | Adapter 有证据证明 Engine 接口收到；不等于进入模型上下文 |
| included | 原生证据或已核实调用语义表明该消息成为某 Execution 输入，关联该 Execution |
| replied | 存在明确关联该消息的回复；无关联的后续文本不能冒充回复 |

若原生仅提供部分证据，其他阶段标为未知，不补造过渡，也不把 delivered 表述为“已理解”。队列去重以产品消息标识为范围；重连及结果未知遵循 [ENG-06](engine-adapter.md#ENG-06)。无运行中介入能力时须使用调用者明确选择的下一轮投递或拒绝策略；默认不得悄悄改投其他 Session。无法等待下一轮的消息应超时并保留原因，而非永远显示已送达。

<a id="COL-04"></a>
**COL-04 协作形式独立组合。** 串行通过依赖约束交付，并行通过隔离工作及整合门槛汇合，交互式通过显式消息与已声明介入能力交流，交接通过新建目标会话延续工作。它们不是实现阶段等级。产品在发起前展示所选组合的能力缺口；任一形式都不要求不同 Harness 共享原生内存、压缩状态或私有上下文。

<a id="COL-05"></a>
**COL-05 Handoff。** 发起方先形成可审阅材料清单：目标、摘要、文件及版本、Diff 基线、TODO、来源和无法迁移项。调度方在目标 Engine、资源权限、披露范围获准后创建新参与者及新 Session，再投递材料，关联源 Task 和 Session。默认不传凭据、原生私有上下文、隐藏推理、内部工具句柄或未授权浏览器状态；历史文本也须按接收范围筛选。目标失败不删除源记录，目标收到材料不等于完成原任务；源执行是否继续或停止必须显式选择，Handoff 本身不隐式终止源执行。

## 共享资源与结果

<a id="COL-06"></a>
**COL-06 一个整合责任入口。** 调度方为每项共享可变资源记录当前工作归属、允许的读写操作、基线及整合责任人。首选为不同参与者使用独立工作副本并提交 Artifact／Diff，由指定整合者串行应用；必须共用资源时，写入或浏览器控制只授予一个当前持有者，其他请求排队或明确拒绝。资源标识与授权见 [CAP-02](shared-capabilities.md#CAP-02)。同一批文件的范围重叠、标签控制权重叠均视作冲突，不能只比较参与者名字。

提交时发布带来源、基线和结果版本的不可变产物引用；整合者检查基线是否仍适用、授权及验收条件。基线变化时必须报告冲突并请求重新整合，禁止静默覆盖。接受结果属于产品验收动作，可由授权用户或预配置确定性检查完成，不能由产物发布者自行伪造。共享路径不能约束 Engine 直接文件写入时，调度方应禁止该并行组合或要求真实隔离；不能声称应用锁已阻止所有外部修改。用户或外部进程的修改同样触发基线复核。

## 失败、取消与用户介入

<a id="COL-07"></a>
**COL-07 控制生效范围可核查。** 用户可查看参与者、Session、执行证据、消息、产物、权限请求和责任链，并请求暂停后续派发、修改尚未接纳的工作或取消 Task。已接纳或执行中的工作改动应以新输入／显式介入表示，保留原记录。取消传播由调度方冻结新委派和待投递消息，对在途 Execution 分别提出停止请求，按[生命周期规则](../domain/lifecycle-and-ownership.md)记录请求与确认。

调度方必须按 [LIFE-03](../domain/lifecycle-and-ownership.md#LIFE-03) 的完整停止判据核对聚合结果，才能报告整个 Task 已停止；远程失联或不支持中止的参与者必须列为仍运行或结果未知。用户也可按 LIFE-03 明确放弃产品协调并归档，保留未知风险、未解除资源限制及必要停止／对账入口；这不属于“整个 Task 已停止”的确认。完成先于取消确认的竞态应保留已完成结果及取消未生效的证据。已发生文件／外部系统变化单列，停止不代表撤销；补偿操作需重新核对授权、现状和副作用，不能作为通用回滚保证。

<a id="COL-08"></a>
**COL-08 部分失败与重试。** 失败参与者保留错误、已有产物和副作用记录，未受依赖影响的分支按 COL-02 继续。调度方展示等待、重试、调整职责或终止的选项及作用范围。原 Execution 不改写为新一次执行；重试建立新 Execution 并关联前次，先确认重试条件及副作用。接纳回执丢失的未决投递及未知结果先查询或核实，不能当成确认失败自动重试；显式放弃协调也不授予重试资格，旧执行及资源冲突仍须核对。整个 Task 的验收依据所有必需分工及整合结果，某个 Engine 正常结束不能自动判定成功；豁免失败分工必须留存授权者与变更后的验收依据。

## 验收场景

用两个可控假 Engine、一组版本化资源和可注入故障的队列验证以下行为；真实 Harness 能力须另行验证。

| 标识 | 场景 | 可观察断言 |
| --- | --- | --- |
| <a id="CO-01"></a>CO-01 | 同 Task 下两个不同 Engine 并行，随后整合 | Session 原 Engine 不变；依赖只在规定结果获接受后解除 |
| <a id="CO-02"></a>CO-02 | Engine 不支持实时介入，发送消息 | 展示并执行明确的排队／拒绝策略；投递与纳入输入证据分开 |
| <a id="CO-03"></a>CO-03 | 两参与者修改重叠文件或控制同标签，外部用户同时更改基线 | 未授权写请求排队／拒绝；整合发现冲突，无静默覆盖 |
| <a id="CO-04"></a>CO-04 | 一分支失败，另一独立分支运行 | 依赖后继阻塞，独立分支遵照策略；重试有新 Execution 和副作用核对 |
| <a id="CO-05"></a>CO-05 | 取消时一执行停止、一执行失联、一执行先行完成 | UI 分别显示证据，不将整个 Task 标为已停止，不承诺回滚 |
| <a id="CO-06"></a>CO-06 | 跨 Engine Handoff，含未授权资料 | 新参与者和新 Session；未授权材料不传递；源状态和迁移缺口保留 |
| <a id="CO-07"></a>CO-07 | 递归委派耗尽预算或引入环依赖 | 新委派被拒并显示原因，现有执行按既定策略处理 |
| <a id="CO-08"></a>CO-08 | 消息 queued 后 Host 重启，送达后断线 | 已承诺持久化的消息可恢复；无证据不补 included／replied，不盲目重发 |
| <a id="CO-09"></a>CO-09 | 远端永久失联，用户先不处置，再明确放弃协调并归档；另一参与者申请写旧资源，随后旧执行迟到完成 | 不自动收尾；显式管理收尾保留未知记录并冻结派发，归档不释放冲突写权限；仅实际终止或隔离证据可解除对应限制，迟到证据更新原事实但不重开任务 |

## 未决项

待批准：默认采用独立工作副本加串行整合，以及同 Session 串行输入的提案。待具体实现验证：哪些执行宿主能强制隔离写入、哪些原生协议提供 included／replied 关联。委派默认额度、队列有效期及任务验收规则应由产品配置明确，不能在 Adapter 内隐式固定。Workflow 编辑与在途实例的版本策略首选“已接纳工作保留原版本，新工作显式采用新版本”，避免编辑追溯改变授权。
