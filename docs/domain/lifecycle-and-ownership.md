# 生命周期与状态归属

- 目的与范围：定义状态权威、生命周期及完成判据；协议载荷、事件重连和行为验收由[接入规格](../specs/engine-adapter.md)与[协作规格](../specs/cross-engine-collaboration.md)负责。
- 设计状态：遵循 [ADR 0002](../decisions/0002-engine-native-and-product-shared-tools-are-distinct.md)、[ADR 0003](../decisions/0003-cross-engine-collaboration-is-task-scoped.md)；以下状态词和转换为 Proposed。
- 实现与验证状态：2026-09-22 仓库尚无相应实现及行为测试；本文件是评审基线，不声称恢复、停止或持久化已经可用。
- 关联文档：[概念与基数](README.md)、[运行与信任边界](../architecture/runtime-and-trust-boundaries.md)、[共享能力](../specs/shared-capabilities.md)。

<a id="LIFE-01"></a>
## LIFE-01 权威状态与身份映射

| 所有者 | 权威内容 | 其他层如何使用 |
| --- | --- | --- |
| 产品 | Task 目标和验收、Workflow 修订、参与者职责和权限、产品 Session 身份、投递记录、执行证据、审批决定、Artifact 来源及版本 | UI 从产品记录生成投影；Adapter 只报告其可观察证据，不代替产品验收 |
| Engine | 原生 Session、私有上下文与压缩、原生工具、原生子 Agent 和原生执行状态 | 产品保存关联和公开事件，不能从聊天文本反推完整原生状态 |
| 执行宿主 | 实际进程、连接、文件访问与隔离措施及执行结果证据 | 产品可记录宿主报告；失去连接不能推导进程退出或副作用撤销 |
| UI、缓存与诊断 | 不持有独立业务权威；显示投影及带来源的诊断 | UI 刷新、缓存失效或日志丢失不得改变业务状态；不以日志猜测补成成功 |

产品 `sessionId` 与原生 Session 标识分开保存，关联包含 Engine、Adapter 版本及执行环境；原生标识仅在其来源范围内唯一。原生执行标识若不可获得应记为未提供，不能杜撰。原生会话恢复成功才可继续原关联；恢复失败后新建原生会话应创建新产品 Session，并关联其前身，不能把历史拼接伪装成恢复。凭据引用与原生身份分开，不把认证秘密当作标识。

<a id="LIFE-02"></a>
## LIFE-02 状态及完成判据（Proposed）

状态表是本文唯一状态词定义。状态变化保存原因和来源证据；连接、可恢复能力、取消请求及观测可信度是独立信息，避免一个状态字段同时表达不同事实。

| 对象 | 状态及含义 | 转换与结束条件 |
| --- | --- | --- |
| Task | `draft` 尚未开始；`active` 正在协作；`waiting` 等待依赖、审批或故障处理；`review` 结果待验收；`accepted` 验收通过；`failed` 已决定终止且失败；`stopped` 已确认停止 | `draft → active`；`active ↔ waiting`；提交完整候选结果后进入 `review`，验收退回可回 `active`；`accepted/failed/stopped` 为本次 Task 终态，不自动重开，后续工作创建关联 Task |
| Agent Instance | `assigned` 已分工；`working` 正在履职；`blocked` 被依赖或异常阻塞；`submitted` 已提交分工结果；`failed` 分工失败；`stopped` 已确认停止 | `assigned → working`，`working ↔ blocked`；结果进入 `submitted` 后整合者可退回 `working`；失败后显式重试可回 `assigned`；停止后继续须显式重新分工，保留历史 |
| Session | `open` 可按能力接受输入；`closing` 正在关闭；`closed` 产品已关闭入口 | `open → closing → closed`；关闭入口不等于删除原生存储或杀死进程，活动执行须另外跟踪。`closed` 不再投递；若原生支持恢复，可显式恢复回 `open` 并保留记录 |
| Execution | `accepted` 输入已接纳等待执行；`running` 已观察到开始；`completed` Engine 确认该输入执行完成；`failed` 执行已结束且报告失败；`stopped` 已确认执行停止 | `accepted → running → completed/failed/stopped`；启动前可直接失败或停止；若原生只提供可信终结事件，可从 `accepted` 直接记终态，不捏造开始事件 |

`unknown` 表示当前执行结果无法确认的观测状态，不是 Execution 终态。产品保留最后确认状态和证据时间，同时显著显示“结果未知”；断线前 `running` 不表示断线后仍在运行，也不表示已停止。后续证据可将观测状态恢复为已知，但不应删除未知时段记录。已确认终态不因迟到的旧事件倒退；互相矛盾的证据进入对账并显示冲突，不能用到达顺序随意覆盖。

<a id="LIFE-INPUT"></a>
### 输入与 Execution 的边界

“已接收”仅指产品记录提交请求；“已接纳”指 Adapter 依据 Engine 接口或受控执行宿主的确切接纳证据确认本次输入将参与执行；新执行输入在此时建立 Execution，运行中介入输入仅关联当前 Execution 并保留独立输入／消息记录，不新建 Execution；“开始执行”须有实际开始证据；“执行完成”须有对应终结证据。队列收件回执不是执行承诺。若 Engine 无单独接纳信号，Adapter 可在确认执行开始或完成时同时确认接纳，并说明证据，不补造时间点。介入消息本身不拥有独立执行终态，其投递及纳入证据与当前 Execution 的终态分开呈现；介入回复不是新的执行完成。输入被拒绝或撤回且尚未接纳时不生成虚假失败 Execution。输入已发送但接纳回执丢失时，保留投递记录并标记接纳结果未知，不杜撰已接纳状态；该记录与未知 Execution 一样阻止 Task 进入终态，须先查询、核实或获得终止证据。

“Engine 完成一轮”至多结束一个 Execution；参与者须提交职责要求的产物才进入 `submitted`；Task 还需指定验收者按目标接受结果才能进入 `accepted`。终态为 `accepted/failed/stopped` 的 Task 均须满足 LIFE-03 的统一终结核对门槛；需要先完成停止或结果对账，期间保留 `waiting`，展示拟结束原因。部分参与者失败可被规则明确视为非必需，但不能掩盖其尚未确认终止的执行。

<a id="LIFE-03"></a>
## LIFE-03 取消、停止与副作用

产品收到取消请求时记录 `cancelRequested`、请求者、作用范围及时间，停止向该范围分派新输入，并逐项传播请求；这不会直接把任何执行变为 `stopped`。执行停止必须有 Engine 或执行宿主可验证的终止证据；不支持中断时显示限制并等待自然结束或用户选择可用控制，不能升级权限强杀。

统一终结核对门槛适用于 Task 的任何终态及 LIFE-05 的删除检查：范围内全部 Execution 已确认终结；接纳回执丢失的未决投递已核实不会再产生未追踪执行；待投递输入已完成处理或撤回；产品控制的共享工具或其他子操作已终结；不存在仍可继续产生动作的未决审批。Task 因取消进入 `stopped` 时，尚未派发的输入须撤回，不能为了清空队列继续派发。Task 可以因取消而 `stopped`，其中某 Execution 却已自然 `completed`；UI 必须保留这个区别。任何远程执行结果未知时，Task 保持等待停止确认，并列出未确认对象。

停止与撤销分离：已写文件、提交、消息或外部变更保留副作用记录。补偿须按具体能力和授权单独执行，记录成功、失败或未知；不得用 Task 的 `stopped` 表示回滚成功。审批被拒绝只禁止被审批动作继续，不自动证明整个 Engine 执行已经停止。

<a id="LIFE-04"></a>
## LIFE-04 断线、恢复及部分失败

UI 关闭不改变产品 Task 或 Engine 状态。Host 重启后从已持久化产品记录重建投影，并向可查询的 Engine 或宿主对账；无法查询时保留未知，不以进程不存在推断远端停止。不支持恢复的 Session 保留可读产品历史，继续工作只能显式新建 Session 并传递获准材料，不能显示“已恢复”。持久化与重连的实现路径见[运行边界](../architecture/runtime-and-trust-boundaries.md)。

一个参与者失败时，产品按 Workflow 中事先声明的必需性和依赖规则阻塞受影响者，其他已授权且无依赖的参与者可以继续。没有规则时默认等待用户或整合责任人决策，不默默跳过必要结果。重试创建新的 Execution，保留与旧执行的因果关联和副作用；结果未知时先对账，不能假设重发安全。重试预算、可安全重发条件及消息阶段由[协作规格](../specs/cross-engine-collaboration.md)定义。

<a id="LIFE-05"></a>
## LIFE-05 归档、删除与历史

归档只是产品视图和保留策略，不取消执行、不删除原生 Session，也不撤销授权。首版建议只允许终态 Task 归档，避免隐藏仍需控制的工作。删除前按 LIFE-03 的统一终结核对门槛检查，包括尚无 Execution 的接纳未知投递、待投递输入、未决审批和共享子操作；任一项未清理或未确认时拒绝删除并列出阻塞对象，允许继续观察、对账和请求停止。产品记录、文件 Artifact、Engine 原生存储和浏览器数据分别按所有者处理，不级联猜测删除。

删除或失去原生数据后，产品保留必要的身份墓碑与不可恢复说明，避免历史关联指向不存在却被复用的身份；具体保留期限和用户彻底删除范围需维护者批准，墓碑不得包含原始敏感内容。Artifact 外部内容被移除或权限撤销时标记不可访问，不能把缺失内容显示成空结果或成功读取。

## 未决问题与验证入口

需要维护者批准状态词、终态 Task 不留未知执行的门槛、归档限制及删除保留策略。不能以本提案替代具体平台的原生恢复核查。验收至少覆盖：没有开始事件而收到终结、断线后迟到完成、拒绝审批但 Engine 仍运行、一个参与者失败而另一个继续、取消后已有文件变化、UI 重开而执行仍未知。另需验证：输入已发出而接纳回执丢失、尚无 Execution 时请求删除，产品必须保留未决投递并拒绝删除；运行中介入获接纳后只有一个 Execution，介入消息保留独立证据且不产生独立执行终态。断言必须分别检查权威记录、UI 投影和副作用，不只检查一个成功标记。
